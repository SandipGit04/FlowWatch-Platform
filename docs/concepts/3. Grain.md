# Grain

**What problem does this solve?**

Grain is what one row in a table represents — "one row = one ___". Without a clear grain,
nobody knows what a row means, and joining two tables with different grains silently
multiplies rows. Counts and revenue come out wrong, with no error message.

**What confused me at first:**

I wrote that "each payment status is grain for one order". That mixed two grains — the
payments table is one row per **attempt**, not one row per order. I also thought that
collapsing payments to one row per order would help me answer the failure rate question.
It is the opposite: collapsing or filtering to successful payments deletes the failed
attempts, so the failure rate can no longer be calculated.

**What made it click:**

1. **The cricket match.** The same match can be stored as ball-by-ball (one row = one
   ball), a batting scorecard (one row = one batsman's innings), or a match result (one
   row = one match). Same truth, three grains. From ball-by-ball you can build the
   scorecard, but from the scorecard you can never find how many sixes Kohli hit in the
   15th over. **Fine → coarse is always possible. Coarse → fine never is.** So raw data
   is stored at the finest grain needed.

2. **The ₹811 bug.** Orders (one row = one order) joined to payments (one row = one
   attempt). Ayan's order had a failed and a successful attempt, so the join produced two
   rows. The order count became 2 and the revenue became ₹811 instead of ₹405.50. Like
   pasting Kohli's "82 runs" next to every one of his 50 balls and adding them up.

3. **The fix.** Say both grains out loud before every join. If they differ, first filter
   or collapse the finer table so it matches the coarser one — but only for that query.
   The fine table stays stored, because the failure rate needs it.

| Table | Grain (one row = …) |
|---|---|
| Events | one event |
| Orders | one order |
| Payments | one payment attempt |
| Rider daily | one rider on one day |
