# Grain

## What problem does this solve?

Grain is **what one row in a table represents**. Without a clear grain, nobody knows
what a row means — and joining two tables with different grains silently copies rows.
Counts and revenue come out wrong, with **no error message**.

---

## 1. Finding the grain — the uniqueness trick

Ask: **which columns together make every row unique?** Add columns one at a time until
no two rows repeat.

| Check | Repeats? |
|---|---|
| `over + ball` | Yes — "over 1, ball 1" happens in every match |
| `match_id + over + ball` | No ✅ |

> **One row = one ball, in one over, in one match.**

---

## 2. Keys, measures, attributes

Every column does one job:

| Type | Job | Cricket example |
|---|---|---|
| 🔑 **Key** | Says **which row** | `match_id`, `over`, `ball` |
| 📏 **Measure** | Says **how much** — a number you add up | `runs` |
| 📝 **Attribute** | **Describes** the row | `bowler` |

- Find the keys first. Measures and attributes are whatever is left.
- **Measures are never part of the grain.** Two balls can both score 4 runs — runs can't
  identify anything.
- Keys are what you `GROUP BY`. Measures are what you `SUM`.

---

## 3. Fine vs coarse

The same cricket match can be stored three ways:

| Table | Grain | Rows |
|---|---|---|
| Ball-by-ball | one ball | ~600 |
| Batting scorecard | one batsman's innings | ~22 |
| Match result | one match | 1 |

> **Fine → coarse is always possible. Coarse → fine never is.**

From ball-by-ball you can build the scorecard. From the scorecard you can never find how
many sixes Kohli hit in the 15th over. So **raw data is stored at the finest grain any
question needs.** Summarise later.

---

## 4. The join bug

Joining two tables with **different grains** copies the coarser row once for every
matching finer row.

| customers (one row = one customer) | orders (one row = one order) |
|---|---|
| C1 Ayan, wallet 500 | C1 has 3 orders |
| C2 Riya, wallet 200 | C2 has 1 order |

Join → 4 rows. `SUM(wallet_balance)` = 500 + 500 + 500 + 200 = **1700**. Correct = **700**.

**The same bug in FlowWatch — the ₹811 bug.** Orders (one row = one order) joined to
payments (one row = one attempt). Ayan's order had a failed and a successful attempt, so
the join produced two rows. The order count became 2 and revenue became **₹811** instead
of **₹405.50**. Like pasting Kohli's "82 runs" next to every one of his 50 balls and
adding them up.

### The fix — make the grains match

1. **Don't join if you don't need to.** Wallet balance lives at customer grain — sum it
   straight from `customers`.
2. **Shrink the finer table first, then join.** Group orders by `customer_id` so both
   tables are one row = one customer.
3. **Filter first, then join.** For FlowWatch revenue, filter payments to
   `status = 'success'` first — then it is one row per order, matching the orders table.

🚫 **`DISTINCT` is not the general fix.** `COUNT(DISTINCT customer_id)` counts customers;
it doesn't fix a sum. `SUM(DISTINCT wallet_balance)` breaks if two customers have the
same balance.

> **The fix for a grain mismatch is to make the grains match — not to hide the copies.**

## 5. Mixed grain — two grains in one table

| date | order_id | amount |
|---|---|---|
| 2026-03-01 | O1 | 300 |
| 2026-03-01 | O2 | 150 |
| 2026-03-01 | TOTAL | 450 |

Some rows are one order, the TOTAL row is one day. `SUM(amount)` = 900 instead of 450.
**Never store totals in the same table** — compute them with `GROUP BY`.

---

## 6. Overall rate ≠ average of rates

| city | orders | late |
|---|---|---|
| Bangalore | 4 | 1 (25%) |
| Kolkata | 2 | 2 (100%) |

- **Overall:** 3 late ÷ 6 orders = **50%**
- **Average of city rates:** (25 + 100) ÷ 2 = **62.5%**

They differ because of **weight** — averaging gives Kolkata's 2 orders the same weight as
Bangalore's 4. Always check which one the question asks for.

---

## 7. Choosing a grain

1. List the questions the table must answer.
2. Find the finest detail any of them needs.
3. That is the grain — not finer (waste), not coarser (can't answer).

Example: a shop needs "best-selling hour" and "best-selling product per day". Only
**one row = one product on one bill** has both `time` and `product`. The bill-level
and day-level tables can both be built from it.

---

## 8. Grain in FlowWatch

| Table | One row = |
|---|---|
| Events | one event |
| Orders | one order |
| Payments | one payment attempt |
| Rider daily | one rider on one day |
| Rider location pings | one rider at one ping time |

- **Revenue** = successful payments only, by `total_amount` — not `quoted_amount`.
  Quoted is what was shown; revenue is what was paid.
- **Payment failure rate** needs every attempt — the fine grain. Filtering to success
  first would delete the failures.

---

## 9. My mistakes — and what I learned

| What I did | What was wrong | Lesson |
|---|---|---|
| Said "each payment status is grain for one order" | Payments are one row per **attempt**, not per order | Don't mix two grains in one sentence |
| Thought collapsing payments would help find the failure rate | Collapsing or filtering to success **deletes** the failed attempts | Store the fine grain; filter or collapse only for the query that needs it |
| "One row = one student detail" | Student S01 had 3 rows | Grain must be exact — use the uniqueness trick |
| "One row = one ping_time" | Two riders shared a ping time | Check uniqueness across **all** rows |
| Put `price`, `marks` in the grain sentence | Those are measures | Grain = keys only |
| Fixed a SUM bug with `COUNT(DISTINCT ...)` | Counts customers, doesn't fix the sum | Match the grains instead |
| Said the bug happened because I "didn't count distinctly" | That's the fix, not the reason | Always explain *why* using grain |
| Used `quoted_amount` for revenue | Revenue = money actually paid | Read the business meaning of each column |
| Gave per-order failure rates | Question asked for one overall rate | Answer the exact question |
| Forgot Riya in the wallet total | Missed a row | Check every row; the number is the result |
| Skipped the measures and final numbers | Unanswered part = wrong | Tick off every part of the question |

---

## Check before every join

- [ ] What is the grain of table A?
- [ ] What is the grain of table B?
- [ ] Are they the same? If not — filter or aggregate first.
- [ ] Am I summing a measure from the coarser table? That's where the copies hurt.

---

## In one sentence

Grain is what one row means, found by the columns that make every row unique; I can
always go from fine to coarse but never back, and before any join I must make both
tables' grains match — otherwise the join copies rows and the numbers come out wrong.
